## How to write (most important rule)

Write so that a 10th-class student can read it once and understand it. The reader is busy and may not know this code.

- Keep sentences short: one idea per sentence, about 15 words or fewer.
- Use common, everyday words:

  | Write | Not |
  |---|---|
  | use | leverage, utilize |
  | check | validate, verify the invariant |
  | change | refactor, rework |
  | start | initialize |

- When you must use a technical word, explain it the first time in a few plain words, e.g. "a mutex (a lock that lets only one thread in at a time)".
- Say what the code does first. Then say why it matters. Use real names, numbers and file paths.
- Use active voice: "The function retries 3 times", not "Retries are performed".
- Use a bullet list when there are 3 or more items.
- Put code names in backticks, like `TokenForUser`, and say in plain words what they are.
- Do not use these words or phrases:
  - seamless, robust, leverage, utilize, delve, crucial, comprehensive, streamline, holistic, paradigm, synergy;
  - "moving part", "surface" (for an API), "seam", "plumbing", "load-bearing", "under the hood", "at a glance";
  - "it's worth noting", "this ensures", "in essence", "overall", "notably", "essentially".
- No hype, no drama, no jokes, no emojis.
- Do not use em dashes (—). Use a full stop or a comma instead.
- Do not repeat the question or add a long intro. Get to the point.
- If you are not sure about something, say so plainly: "I could not confirm this. Check X."
